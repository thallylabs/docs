Software teams ship continuously, but the places where customers learn about
the product are maintained separately. A single change can create work across
documentation, API and SDK references, tutorials, release notes, examples, and
AI context. The usual failure is not writing quality—it is that no system owns
finding all of that communication work.

Thally is built to own that handoff.

> Every product change. Every knowledge surface. Automatically in sync.

That is the direction of the product. The working loop connects GitHub product
changes to an evidence-backed product map, explains which documentation is
affected, and prepares a pull request for a person to review.

## How it works today

<Steps>
  <Step title="A product change supplies the evidence">
    After a product pull request merges, Thally reads the exact merged commit.
    It extracts supported facts from OpenAPI, MDX, and TypeScript without
    running customer code, and keeps a link to the file evidence.
  </Step>
  <Step title="Thally explains what the change affects">
    The Product Knowledge Graph compares the new facts with the previous
    version. Impact analysis keeps a docs page only when a supported graph path
    and evidence explain why it may need work.
  </Step>
  <Step title="Track updates the affected source">
    Track receives a limited list of pages and evidence, updates the relevant
    MDX in a disposable sandbox, and validates the result with `thally check`.
    If no docs are affected, the loop stops without AI work or a pull request.
  </Step>
  <Step title="A person decides what publishes">
    The result is a normal pull request. Reviewers can accept, correct, or
    reject it; the agent never merges its own work.
  </Step>
  <Step title="One reviewed source feeds every output">
    After approval, the content engine serves the same structured source as
    HTML, Markdown, JSON, JSON-LD, search, embeddings, and agent context.
  </Step>
</Steps>

## The trust contract

<Columns cols={2}>
  <Card title="The product is the source of truth" icon="code-simple">
    The pipeline begins with reviewed product evidence, not an ungrounded
    request to generate content.
  </Card>
  <Card title="Understand before generating" icon="link-simple">
    A change should produce communication work only after Thally can explain
    what customer-facing knowledge it affects.
  </Card>
  <Card title="Evidence before confidence" icon="book-open">
    The proposed update keeps the product context available for reviewers
    instead of presenting generated prose as fact.
  </Card>
  <Card title="Humans approve important communication" icon="message">
    Review remains a product invariant. Automation removes discovery and
    drafting work, not accountability.
  </Card>
</Columns>

## Current boundary and direction

| Area | Available now | Product direction |
| --- | --- | --- |
| Product source | Connected GitHub repositories with OpenAPI, MDX, and TypeScript evidence | More source types and integrations |
| Product understanding | Versioned product facts and links tied to exact commits and inspectable evidence | Broader fact coverage across product tools |
| Knowledge surface | Documentation pages and API-reference content in a Thally project | SDK references, tutorials, release notes, examples, and other customer-facing surfaces |
| Output | Explained impact results and evidence-checked documentation pull requests | Coordinated updates across every affected surface |
| Approval | Existing GitHub review and deployment workflow | Human control over every important communication |
| Learning | Reviewer corrections improve later ranking after enough examples exist | More useful team-specific ranking without weakening evidence rules |

<Note type="info" title="Not another knowledge destination">
Thally includes an open documentation engine, but the product is not trying to
be another wiki, CMS, or knowledge base. Those tools store knowledge. Thally's
job is to keep it synchronized as the product changes.
</Note>

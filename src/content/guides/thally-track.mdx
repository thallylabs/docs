Every product change creates communication work. Thally Track finds the part
that belongs in customer-facing documentation and prepares a pull request for
your team to review.

Track is a Thally Cloud service. It connects verified GitHub changes to the
Product Knowledge Graph, uses evidence-backed impact analysis to select the
documentation that may need work, and runs the docs agent inside an isolated
environment. It never auto-merges its pull requests.

## Product sources and Knowledge surfaces

These connections have different jobs:

| Connection | What it contributes | What Thally may do |
| --- | --- | --- |
| **Product source** | Product code and specifications that Track observes | Read an exact revision, extract evidence, and calculate documentation impact |
| **Primary docs repository** | The documentation site connected to the Thally site | Open a review-gated docs pull request; publish the exact merged revision when managed hosting is enabled |
| **Knowledge surface** | Another explicitly connected Markdown or MDX repository | Open a scoped draft pull request; never deploy the repository |

The primary docs repository cannot also be one of its own Product sources. That
hard boundary prevents a documentation update from looking like a new product
change and creating a loop.

## Connect Product sources

You can connect Product sources while creating a site or later from the site's
settings.

<Steps>
  <Step title="Open Product sources">
    In Thally Cloud, open the site and select **Track**. Owners and editors can
    manage the connected repositories from that page.
  </Step>
  <Step title="Authorize the repository">
    Install or update the Thally GitHub App for the account that owns the
    product repository. Thally revalidates access with a short-lived
    installation token whenever it needs the repository.
  </Step>
  <Step title="Choose the source policy">
    Select the repository and base branch. Add path filters when only part of a
    monorepo represents the product surface Track should observe. You can also
    choose the destination tab and group where new primary-documentation pages
    from this source should appear.
  </Step>
  <Step title="Save the connection">
    Future matching GitHub deliveries can now create immutable product
    snapshots and impact runs for this site.
  </Step>
</Steps>

Each Product source keeps its own repository, branch, optional path filters,
destination tab and group placement, and enabled state. A site can connect
multiple sources so an API, SDK, and web application can contribute to the
same product model without sharing mutable repository state.

## Connect Knowledge surfaces

Use Knowledge surfaces when a product change may also require an update in a
separate Markdown or MDX repository—for example SDK guides, tutorials, or
release notes.

When Knowledge surfaces are available for the workspace, open **Site settings
→ Knowledge surfaces**, choose a repository that the Thally GitHub App can
access, and confirm:

- the base branch;
- the repository root Track may inspect;
- the exact Markdown or MDX paths Track may change;
- the validation policy; and
- any administrator instructions for that destination.

Thally records those boundaries with each run. Pausing or removing a surface
affects future product changes without invalidating a run that has already
been claimed or orphaning an open pull request.

<Note type="info" title="A Knowledge surface is not another managed site">
Thally may open a scoped draft pull request in the connected repository, but
it never runs that repository's dependencies, scripts, generators, or
workflows and never deploys it. The repository's own team reviews and ships the
change through its normal process.
</Note>

## What triggers Track

Track supports two explicit modes:

### Merged product changes

When a pull request merges into a connected Product source's configured base
branch, the shared Thally GitHub webhook verifies and durably records the
delivery. Track reserves the run idempotently and ties every later step to the
exact merged revision.

### Preview product changes

An explicitly labelled preview pull request can ask Track to prepare docs
before the product change merges. Preview runs remain separate from merged
production runs, so an unmerged revision cannot silently become production
product knowledge. Preview runs do not fan out to connected Knowledge
surfaces; those destinations are updated only from merged product changes.

## How a Track run works

<Mermaid>{`
sequenceDiagram
    participant GH as Product repository
    participant Cloud as Thally Cloud
    participant Graph as Product Knowledge Graph
    participant Worker as Track Worker
    participant Docs as Documentation repository
    participant Person as Reviewer

    GH->>Cloud: Signed merged or labelled-preview PR event
    Cloud->>Cloud: Store and claim the verified delivery
    Cloud->>Graph: Ingest the exact source revision
    Graph->>Cloud: Return an evidence-backed impact bundle
    alt No tracked impact
        Cloud-->>GH: Complete without model work or a pull request
    else Documentation may need work
        Cloud->>Worker: Send a bounded, encrypted job claim
        Worker->>Worker: Edit and validate in a disposable Sandbox
        Worker->>Docs: Open a review-gated pull request
        Person->>Docs: Review, edit, merge, or reject
        Docs->>Cloud: Verified merge event
        Cloud->>Cloud: Publish the exact docs commit when managed
    end
`}</Mermaid>

The impact bundle contains the product revision, semantic changes, ranked
target pages, evidence, and policy version. A vector or text match may suggest
a page, but evidence and a supported product-to-documentation path are what
make it eligible for the run.

The Track Worker receives an opaque queue capability rather than a reusable
credential. The job is encrypted at rest. Provider model keys and the GitHub
App private key remain in trusted control-plane services; the disposable
Sandbox gets only the bounded context and destination-scoped access it needs.

## Review and publication

Track's output is a normal GitHub pull request. Reviewers can change, accept,
or reject it. The activity record keeps the source revision and evidence that
led to the proposal, while private job instructions and credentials never
enter the repository.

For the primary docs repository, merging the pull request creates a verified
GitHub event for the exact docs commit. A managed site then uses the normal
content-only or full-build pipeline, smoke-checks the immutable candidate, and
moves the live release pointer only after validation succeeds.

Connected Knowledge surfaces stop at the merged draft pull request. Thally
does not publish or otherwise operate the connected repository.

## Safety and failure behavior

- GitHub signatures are verified before a delivery is accepted.
- Delivery IDs and Track run reservations make retries idempotent.
- Archives, selected files, prompt context, output, and run attempts are
  bounded.
- Product extraction never installs dependencies or executes customer code.
- The runner may edit only allowed documentation paths.
- A no-impact result completes without model use or a pull request.
- A failed Track run cannot change the live documentation release.
- The agent never auto-merges.

## Self-hosted authoring tools

The public `thally` CLI, docs agent, and MCP server can still help a developer
prepare documentation locally. Those authoring tools are separate from the
canonical Cloud Track pipeline described here. You do not need to expose a
Track webhook from the documentation runtime or store a product-repository PAT
inside a managed site.
